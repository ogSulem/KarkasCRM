# Развёртывание КаркасCRM

Документ для администратора сервера: установка, домен и HTTPS, резервные копии, диагностика и требования безопасности. Пользовательская инструкция по работе в интерфейсе — в файле [ИНСТРУКЦИЯ.md](ИНСТРУКЦИЯ.md).

## 1. Требования

- Сервер Linux с публичным IP (для работы вебхуков мессенджеров и почты).
- Docker Engine и Docker Compose v2.
- Для доменного режима: домен, A-запись которого указывает на IP сервера, открытые порты 80 и 443.
- Без Docker (вариант для отладки): Node.js 22.5 или новее.

Для начального тестирования ориентир — 1 vCPU и 1 ГБ оперативной памяти (не гарантия для 100 одновременных сотрудников); данные занимают мегабайты, так что диск по объёму определяется резервными копиями и вложениями.

## 2. Два режима работы

| Режим | Команда | Доступ | Назначение |
| --- | --- | --- | --- |
| Локальный / по IP | `./install.sh` | `http://сервер:8080` | Внутренняя сеть, проверка, работа за своим VPN |
| С доменом и HTTPS | `./install.sh --tls crm.example.ru mail@example.ru` | `https://crm.example.ru` | Боевой сервер для сотрудников и вебхуков |

В доменном режиме поднимается только reverse-proxy Caddy с портами 80/443, а порт приложения 8080 закрывается от внешней сети (`CRM_BIND=127.0.0.1`). Caddy сам выпускает и продлевает сертификат Let's Encrypt.

## 3. Установка

```bash
git clone https://github.com/ogSulem/KarkasCRM.git
cd KarkasCRM
./install.sh --tls crm.example.ru admin@example.ru
```

Установщик:

1. создаёт файл `.env` из шаблона `.env.example`;
2. генерирует секрет подписи сессий (`JWT_SECRET`) и пароль администратора;
3. собирает образ и запускает контейнер;
4. в доменном режиме дополнительно поднимает Caddy и ждёт выпуска сертификата;
5. дожидается ответа `GET /api/health` и показывает адрес системы и пароль администратора.

Сохраните пароль администратора из вывода установщика. После первого входа его можно сменить в **Настройки → Профиль**.

## 4. Параметры окружения

Файл `.env` создаётся установщиком и в репозиторий не попадает. Основные параметры:

| Параметр | Назначение |
| --- | --- |
| `CRM_PORT` | Порт на сервере, по которому открывается система (по умолчанию 8080) |
| `CRM_BIND` | Адрес прослушивания: `0.0.0.0` — доступ извне, `127.0.0.1` — только через reverse-proxy |
| `TZ` | Часовой пояс: влияет на даты, отчёты и время резервных копий |
| `CRM_DOMAIN`, `ACME_EMAIL` | Домен и почта для сертификата Let's Encrypt (режим TLS) |
| `JWT_SECRET` | Секрет подписи сессий, 32+ случайных символа. Если не задан, система создаёт постоянный секрет в каталоге данных |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Учётная запись первого администратора (создаётся только при пустой базе) |
| `SEED_MODE` | Начальные данные: `demo` (примеры, локально), `base` (правовая основа, прод), `off` (пусто). Пусто = авто: с доменом — `base`, без — `demo` |
| `WAZZUP_API_KEY`, `WAZZUP_WEBHOOK_SECRET` | Ключ и секрет вебхука Wazzup (можно ввести и в интерфейсе) |
| `SMTP_*`, `MAIL_FROM`, `EMAIL_WEBHOOK_SECRET` | Почта: отправка писем и приём входящих (можно ввести и в интерфейсе) |

Остальное **не требует правки .env** и настраивается в интерфейсе:
план продаж, автосоздание сделок и автораспределение, срок и час резервных
копий, уведомления о просроченных задачах, лимит попыток входа,
встраивание в iframe (там же: `frame_ancestors` — список сайтов, которым
разрешено открывать CRM во фрейме; пусто — запрещено, `*` — любой сайт),
ключи источников конкурентов и шаблоны сообщений.

**Настройки из интерфейса перекрывают .env.** Всё, что меняется в разделе
«Настройки», сохраняется в базе данных и имеет приоритет над значениями
окружения. `.env` задаёт только первоначальные значения при первом запуске
на пустой базе — править его после настройки через интерфейс не нужно
(и бесполезно: CRM прочитает значение из базы).

Сгенерировать сильный секрет вручную:

```bash
openssl rand -hex 32
```

## 5. HTTPS вручную

### Caddy в Docker (рекомендуется)

Конфигурация уже лежит в `deploy/Caddyfile`, сервис описан в `docker-compose.yml` под профилем `tls`:

```bash
# в .env: CRM_DOMAIN=crm.example.ru, CRM_BIND=127.0.0.1
# JWT_SECRET — случайный, от 32 символов; ADMIN_PASSWORD — уникальный, от 12 символов
docker compose --profile tls up -d --build
```

### Внешний Caddy или nginx

Если reverse-proxy уже работает на сервере, оставьте `CRM_BIND=127.0.0.1` и проксируйте на `127.0.0.1:8080`. Обязательно передавайте заголовок `X-Forwarded-Proto: https` — по нему система включает флаг Secure у cookie и HSTS. Пример для nginx:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

## 6. Настройка после установки

Дальше всё делается в интерфейсе, без правки кода:

1. Смените пароль администратора: **Настройки → Профиль**.
2. Загрузите логотип компании: **Настройки → Данные и компания → Логотип компании**.
3. Подключите каналы: **Настройки → Интеграции и каналы** — Wazzup (WhatsApp, Telegram, Instagram, Viber одним ключом) и почта SMTP.
4. Приведите в порядок воронку: **Настройки → Воронки и этапы**.
5. При необходимости добавьте сотрудников и роли: **Настройки → Команда**.
6. Заполните реквизиты для документов: **Настройки → Реквизиты для КП и счёта**.

### Начальные данные

Профиль `tls` (install.sh --tls) ставит `SEED_MODE=base`: каталог позиций,
личные шаблоны администратора и пример правила автоматизации — правовая основа, с которой
не надо начинать с нуля. Всё это редактируется в интерфейсе как обычные
данные. Локальный запуск по умолчанию получает `SEED_MODE=demo` — живые
примеры клиентов, сделок, задач и чатов; удаляются кнопкой **Настройки →
Данные и компания → Демонстрационные данные**. Для совсем чистой базы:
`SEED_MODE=off`.

## 7. Резервные копии и восстановление

- Автоматические копии базы создаются ежесуточно; час и срок хранения задаются в интерфейсе: **Настройки → Данные и компания → Обслуживание и уведомления**. Файлы лежат в каталоге данных `backups/`.
- Ручная копия создаётся в **Настройки → Данные и компания → Резервные копии базы**.
- Перед каждым обновлением схемы система сама делает копию `pre-upgrade-…`.
- Восстановление запускается из того же раздела: текущая база заменяется, служба перезапускается автоматически в Docker (`restart: unless-stopped`). При запуске без Docker процесс нужно поднять заново командой `./run-local.sh`.
- Дополнительно каталог `/data` смонтирован в именованный том `karkascrm_data` — его стоит включить в систему бэкапов хостинг-провайдера или забирать по расписанию:

```bash
# пример ночной копии тома на хост
docker run --rm -v karkascrm_data:/data -v "$HOME/backups":/backup alpine \
  tar czf "/backup/karkas-$(date +%F).tar.gz" -C /data .
```

## 8. Обновление

```bash
./scripts/update.sh
```

Скрипт забирает изменения из репозитория, пересобирает контейнер и перезапускает сервис. Данные не затрагиваются, перед миграцией схемы автоматически создаётся страховочная копия.

## 9. Диагностика

```bash
docker compose ps                 # статус контейнеров
docker compose logs -f crm        # логи приложения
docker compose --profile tls logs -f caddy   # логи HTTPS-прокси
curl -s http://127.0.0.1:8080/api/health     # проверка приложения
```

Типовые причины недоступности:

- сертификат не выпускается — проверьте DNS домена и открытые порты 80/443;
- не приходят вебхуки — проверьте публичный адрес и секрет вебхука в настройках канала;
- не отправляется почта — нажмите «Отправить тестовое письмо» в настройках почты, ответ сервера покажет причину;
- вход не принимается — после серии неудачных попыток IP временно ограничивается, счётчик сбрасывается через 5 минут.

## 10. Контрольный список безопасности

- [ ] `JWT_SECRET` задан длинной случайной строкой, пароль администратора сменён.
- [ ] Боевой сервер работает только по HTTPS, `CRM_BIND=127.0.0.1`.
- [ ] Сотрудникам выданы роли по принципу минимальных прав, бывшие сотрудники деактивированы.
- [ ] Резервные копии настроены и проверено восстановление.
- [ ] Сервер получает обновления безопасности ОС и Docker.
- [ ] Ключи интеграций хранятся в `.env` с правами `600` либо введены через интерфейс.

## 11. Запуск без Docker

Для разработки или отладки достаточно Node.js:

```bash
./run-local.sh                      # http://localhost:8080, база в ./data
PORT=3000 ADMIN_PASSWORD=пароль ./run-local.sh
```

Пример unit-файла systemd для постоянного запуска без Docker:

```ini
[Unit]
Description=KarkasCRM
After=network.target

[Service]
WorkingDirectory=/opt/KarkasCRM
Environment=NODE_ENV=production
ExecStart=/usr/bin/node --experimental-sqlite backend/src/server.js
Restart=always
User=karkas

[Install]
WantedBy=multi-user.target
```

## Локальная проверка без настроек

`docker compose up --build` работает без `.env` и домена: http://localhost:8080.
Порт по умолчанию привязан к 127.0.0.1. Учётные данные первого входа:
`admin@example.com` / `admin12345` — только для локального теста.
Профиль `tls` проверяет наличие домена и нешаблонных секретов при запуске Caddy.
Эти проверки не заменяют настройку firewall, DNS и смену пароля в уже существующей базе.
Для тестовых данных и формата таблиц см. README; результаты аудита — AUDIT.md.

## Проверка после TLS-запуска

```bash
docker compose --profile tls ps
docker compose logs --tail=100 crm caddy
curl --fail https://crm.example.ru/.well-known/health
```

Замените домен в последней команде своим. Проверьте вход, создание сотрудника,
обязательную смену пароля, загрузку файла и резервную копию. Если сертификат не
выдан, проверьте A/AAAA, firewall и доступность 80/443 извне. `ACME_EMAIL` необязателен;
если заполнен, скрипт передаёт его Caddy. Домен указывайте без протокола, порта и пути,
кириллические домены — в punycode. Секреты с `$` в `.env` заключайте в одинарные кавычки,
чтобы Compose не интерполировал их; проще использовать сгенерированные hex-строки.
Не переносите локальную тестовую базу с известным паролем в production: изменение
`ADMIN_PASSWORD` в `.env` не меняет пароль уже существующего администратора.
