# Развёртывание КаркасCRM

Документ для администратора сервера: установка, домен и HTTPS, резервные копии, диагностика и требования безопасности. Пользовательская инструкция по работе в интерфейсе — в файле [ИНСТРУКЦИЯ.md](ИНСТРУКЦИЯ.md).

## 1. Требования

- Сервер Linux с публичным IP (для работы вебхуков мессенджеров и почты).
- Docker Engine и Docker Compose v2.
- Для доменного режима: домен, A-запись которого указывает на IP сервера, открытые порты 80 и 443.
- Без Docker (вариант для отладки): Node.js 22.5 или новее.

Для начального тестирования ориентир — 1 vCPU и 1 ГБ оперативной памяти (не гарантия для 100 одновременных сотрудников); данные занимают мегабайты, так что диск по объёму определяется резервными копиями и вложениями.

## 2. Два режима работы

| Режим | Команда | Доступ | Назначение |
| --- | --- | --- | --- |
| Локальный / по IP | `./install.sh` | `http://сервер:8080` | Внутренняя сеть, проверка, работа за своим VPN |
| С доменом и HTTPS | `./install.sh --tls crm.example.ru mail@example.ru` | `https://crm.example.ru` | Боевой сервер для сотрудников и вебхуков |

В доменном режиме поднимается только reverse-proxy Caddy с портами 80/443, а порт приложения 8080 закрывается от внешней сети (`CRM_BIND=127.0.0.1`). Caddy сам выпускает и продлевает сертификат Let's Encrypt.

## 3. Установка

```bash
git clone https://github.com/ogSulem/KarkasCRM.git
cd KarkasCRM
./install.sh --tls crm.example.ru admin@example.ru
```

Установщик:

1. создаёт файл `.env` из шаблона `.env.example`;
2. генерирует секрет подписи сессий (`JWT_SECRET`) и пароль администратора;
3. собирает образ и запускает контейнер;
4. в доменном режиме дополнительно поднимает Caddy и ждёт выпуска сертификата;
5. дожидается ответа `GET /api/health` и показывает адрес системы и пароль администратора.

Сохраните пароль администратора из вывода установщика. После первого входа его можно сменить в **Настройки → Профиль**.

## 4. Параметры окружения

Файл `.env` создаётся установщиком и в репозиторий не попадает. Основные параметры:

| Параметр | Назначение |
| --- | --- |
| `CRM_PORT` | Порт на сервере, по которому открывается система (по умолчанию 8080) |
| `CRM_BIND` | Адрес прослушивания: `0.0.0.0` — доступ извне, `127.0.0.1` — только через reverse-proxy |
| `TZ` | Часовой пояс: влияет на даты, отчёты и время резервных копий |
| `CRM_DOMAIN`, `ACME_EMAIL` | Домен и почта для сертификата Let's Encrypt (режим TLS) |
| `JWT_SECRET` | Секрет подписи сессий, 32+ случайных символа. Если не задан, система создаёт постоянный секрет в каталоге данных |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Учётная запись первого администратора (создаётся только при пустой базе) |
| `SEED_MODE` | Начальные данные: `demo` (примеры, локально), `base` (правовая основа, прод), `off` (пусто). Пусто = авто: с доменом — `base`, без — `demo` |
| `WAZZUP_API_KEY`, `WAZZUP_WEBHOOK_SECRET` | Ключ и секрет вебхука Wazzup (можно ввести и в интерфейсе) |
| `SMTP_*`, `MAIL_FROM`, `EMAIL_WEBHOOK_SECRET` | Почта: отправка писем и приём входящих (можно ввести и в интерфейсе) |
| `PUBLIC_URL` | Публичный адрес CRM для ссылок и вебхуков. Обычно не нужен: берётся из `CRM_DOMAIN` или из адреса браузера; можно задать в интерфейсе |
| `LOGO_FILE` | Свой файл логотипа внутри контейнера (обычно проще загрузить логотип в интерфейсе) |
| `ALLOW_PRIVATE_FETCH` | `1` — разрешить проверке конкурентов локальные адреса (для тестов и внутренних шлюзов) |
| `KARKAS_NO_SEED` | `1` — не создавать начальные данные вообще |

Остальное **не требует правки .env** и настраивается в интерфейсе:
план продаж, автосоздание сделок и автораспределение, срок и час резервных
копий, уведомления о просроченных задачах, лимит попыток входа,
встраивание в iframe (там же: `frame_ancestors` — список сайтов, которым
разрешено открывать CRM во фрейме; пусто — запрещено, `*` — любой сайт),
ключи источников конкурентов и шаблоны сообщений.

**Настройки из интерфейса перекрывают .env.** Всё, что меняется в разделе
«Настройки», сохраняется в базе данных и имеет приоритет над значениями
окружения. `.env` задаёт только первоначальные значения при первом запуске
на пустой базе — править его после настройки через интерфейс не нужно
(и бесполезно: CRM прочитает значение из базы).

Сгенерировать сильный секрет вручную:

```bash
openssl rand -hex 32
```

## 5. HTTPS вручную

### Caddy в Docker (рекомендуется)

Конфигурация уже лежит в `deploy/Caddyfile`, сервис описан в `docker-compose.yml` под профилем `tls`:

```bash
# в .env: CRM_DOMAIN=crm.example.ru, CRM_BIND=127.0.0.1
# JWT_SECRET — случайный, от 32 символов; ADMIN_PASSWORD — уникальный, от 12 символов
docker compose --profile tls up -d --build
```

### Внешний Caddy или nginx

Если reverse-proxy уже работает на сервере, оставьте `CRM_BIND=127.0.0.1` и проксируйте на `127.0.0.1:8080`. Готовый конфиг — `deploy/nginx.conf` (там же передача реального IP и настройки для живых событий чатов). Обязательно передавайте `X-Forwarded-Proto: https` — по нему система включает флаг Secure у cookie и HSTS. Пошаговый сценарий для сервера с уже занятыми 80/443 — в разделе 5.1.

## 5.1. Сервер, где уже работает другой сайт

Частый случай: на VPS уже крутится сайт (nginx/apache) и порты 80/443 заняты.
Ставить рядом второй веб-сервер, который тоже захочет 80/443, нельзя — они
будут конфликтовать. Правильный путь: CRM слушает только localhost, а
существующий nginx проксирует на неё отдельный поддомен.

### Шаг 1. Посмотреть, что уже занято

```bash
# кто слушает 80/443/8080 (нужен root или sudo)
sudo ss -ltnp | grep -E ':(80|443|8080)\b'
# то же через docker, если сайт в контейнерах
docker ps --format 'table {{.Names}}\t{{.Ports}}'
# и через systemd
systemctl list-units --type=service --state=running | grep -E 'nginx|apache|caddy'
```

Типичный ответ: `nginx` на `0.0.0.0:80` и `0.0.0.0:443`. Значит, порты
трогать не нужно — CRM встанет на свободный `127.0.0.1:8080`.

### Шаг 2. Выбрать свободный порт для CRM

Если 8080 тоже занят (например, другим приложением), возьмите 8090:

```bash
sudo ss -ltnp | grep ':8090' || echo "8090 свободен"
```

### Шаг 3. Поднять CRM без профиля tls

```bash
cd /opt/KarkasCRM          # папка, куда склонирован репозиторий
# в .env:
#   CRM_DOMAIN=crm.вашдомен.ру   (нужен для режима «боевые данные» и ссылок)
#   CRM_BIND=127.0.0.1           (снаружи CRM не видна)
#   CRM_PORT=8080                (или 8090, если 8080 занят)
docker compose up -d --build
curl -s http://127.0.0.1:8080/api/health   # {"ok":true,...}
```

Профиль `tls` **не включаем**: Caddy не запустится, порты 80/443 останутся у
вашего сайта, конфликта не будет.

### Шаг 4. Добавить поддомен в существующий nginx

1. В DNS создайте A-запись `crm.вашдомен.ру` → IP сервера.
2. Скопируйте `deploy/nginx.conf` в `/etc/nginx/sites-available/crm.conf`,
   замените `server_name` и порт в `proxy_pass` (если выбрали 8090).
3. Включите сайт и проверьте конфигурацию:

```bash
sudo ln -s /etc/nginx/sites-available/crm.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

4. Выпустите сертификат на новый поддомен (основной сайт не затрагивается):

```bash
sudo certbot --nginx -d crm.вашдомен.ру
```

5. Откройте `https://crm.вашдомен.ру`. В **Настройки → Интеграции** проверьте
   «Адрес CRM в интернете» — там должен быть этот домен: он подставляется в
   адреса вебхуков Wazzup, формы сайта и приёма писем.

Блок `location` из `deploy/nginx.conf` уже передаёт реальный IP клиента
(`X-Forwarded-For`) — без него лимиты входа считались бы на всех сотрудников
как на один адрес, и подъезд офиса упирался бы в ограничение.

### Шаг 5. Закрыть лишние порты

Наружу должны смотреть только 22 (SSH), 80 и 443 (ваш nginx). Порт CRM
(`8080`/`8090`) привязан к `127.0.0.1` и из интернета недоступен — проверьте:

```bash
sudo ufw status                    # или firewall-cmd --list-all
curl -m 3 http://ВАШ_ПУБЛИЧНЫЙ_IP:8080/ || echo "снаружи закрыт — так и должно быть"
```

### Если 80/443 свободны

Тогда проще штатный вариант с Caddy:

```bash
./install.sh --tls crm.вашдомен.ру mail@вашдомен.ру
```

Caddy сам выпустит сертификат и будет проксировать на CRM. Ничего в nginx
настраивать не нужно. Не запускайте одновременно `--profile tls` и свой
nginx на 80/443 — будет ошибка «address already in use».

### Если домена нет вообще

CRM можно открыть по `http://IP:8080`: в `.env` поставьте `CRM_BIND=0.0.0.0`
и откройте 8080 в firewall. Это подходит для работы в офисе/VPN, но **не для
вебхуков Wazzup и формы с сайта**: им нужен HTTPS-адрес. Для боевого
использования нужен домен и сертификат.

## 6. Настройка после установки

Дальше всё делается в интерфейсе, без правки кода:

1. Смените пароль администратора: **Настройки → Профиль**.
2. Загрузите логотип компании: **Настройки → Данные и компания → Логотип компании**.
   Загруженный файл хранится в томе `/data/logo` и перекрывает логотип из комплекта;
   он переживает пересборку образа и обновления. Чтобы вернуться к стандартному —
   кнопка «Удалить логотип» рядом. (Продвинутый вариант: смонтировать свой файл и
   указать `LOGO_FILE=/путь/в/контейнере.png` — он имеет приоритет над загрузкой.)
3. Подключите каналы: **Настройки → Интеграции и каналы** — Wazzup (WhatsApp, Telegram, Instagram, Viber одним ключом) и почта SMTP.
4. Приведите в порядок воронку: **Настройки → Воронки и этапы**.
5. При необходимости добавьте сотрудников и роли: **Настройки → Команда**.
6. Заполните реквизиты для документов: **Настройки → Реквизиты для КП и счёта**.

### Начальные данные

Профиль `tls` (install.sh --tls) ставит `SEED_MODE=base`: каталог позиций,
личные шаблоны администратора и пример правила автоматизации — правовая основа, с которой
не надо начинать с нуля. Всё это редактируется в интерфейсе как обычные
данные. Локальный запуск по умолчанию получает `SEED_MODE=demo` — живые
примеры клиентов, сделок, задач и чатов; удаляются кнопкой **Настройки →
Данные и компания → Демонстрационные данные**. Для совсем чистой базы:
`SEED_MODE=off`.

### Что уже настроено в образе

- приложение работает от непривилегированного пользователя `node` (uid 1000), корень
  контейнера только для чтения — данные пишутся исключительно в том `/data`;
- сняты все Linux-возможности (`cap_drop: ALL`), включён `no-new-privileges`;
- логи ограничены (10 МБ × 3 файла), чтобы диск не заполнился за месяцы работы;
- `restart: unless-stopped` + healthcheck: контейнер сам поднимается после сбоя и перезагрузки;
- `stop_grace_period: 20s`: при остановке сервер успевает дописать журнал SQLite и закрыть базу;
- домен (`CRM_DOMAIN`) передаётся внутрь приложения, поэтому авто-режим на сервере
  выбирает `base`, а не `demo`.
- базовый образ задан переменной сборки: чтобы зафиксировать точную версию Node,
  соберите `docker compose build --build-arg NODE_IMAGE=node:22.22.3-alpine`
  (или digest `node@sha256:…`), затем `docker compose up -d`.

## 7. Резервные копии и восстановление

> **Важно.** Никогда не запускайте `docker compose down -v`: ключ `-v` удаляет
> том `karkascrm_data` вместе с базой и всеми резервными копиями. Безопасная
> остановка — `docker compose stop` или `docker compose down` **без** `-v`.
> Резервные копии лежат в том же томе, поэтому раз в сутки забирайте их на
> другой сервер или в объектное хранилище (см. ниже) — иначе сбой диска
> унесёт и данные, и копии.



- Автоматические копии базы создаются ежесуточно; час и срок хранения задаются в интерфейсе: **Настройки → Данные и компания → Обслуживание и уведомления**. Файлы лежат в каталоге данных `backups/`.
- Ручная копия создаётся в **Настройки → Данные и компания → Резервные копии базы**.
- Перед каждым обновлением схемы система сама делает копию `pre-upgrade-…`.
- Восстановление запускается из того же раздела: текущая база заменяется, служба перезапускается автоматически в Docker (`restart: unless-stopped`). При запуске без Docker процесс нужно поднять заново командой `./run-local.sh`.
- Дополнительно каталог `/data` смонтирован в именованный том `karkascrm_data` — его стоит включить в систему бэкапов хостинг-провайдера или забирать по расписанию:

```bash
# пример ночной копии тома на хост
docker run --rm -v karkascrm_data:/data -v "$HOME/backups":/backup alpine \
  tar czf "/backup/karkas-$(date +%F).tar.gz" -C /data .
```

### 7.1. Копии на другом сервере: облачное хранилище (S3)

Копии в каталоге `backups/` защищают от ошибки «удалил не то», но не от поломки
диска или потери всего сервера: они лежат на той же машине. Настоящая страховка —
вторая копия **в другом месте**. Самый простой и дешёвый вариант — объектное
хранилище S3 (у Рег.ру — «Объектное хранилище», в других облаках — «S3»).

Простыми словами: это «ведро» для файлов в чужом надёжном дата-центре. Вы кладёте
туда файл по ключу `karkascrm/crm-2026-10-20-0300.db`, платите только за занятое
место, а скачать файл можно в любой момент через панель или ссылку.

**Сколько это стоит и сколько места нужно.** База каркасной компании — обычно
10–100 МБ; за год ежедневных копий набирается 1–3 ГБ (старые копии CRM удаляет
сама по сроку хранения). У Рег.ру оплата идёт с баланса облака по занятому месту
(порядка 1–3 ₽ за гигабайт в месяц), у других провайдеров — от 55 ₽/мес за 20 ГБ.
То есть 100–200 ₽ в месяц. Никаких серверов для этого держать не нужно.

**Как включить (Рег.ру):**

1. В панели облака создайте **объектное хранилище** (ведро) с именем, например,
   `karkas-backups`, и запомните адрес из панели — у Рег.ру он вида
   `https://s3.regru.cloud`.
2. Создайте **ключи доступа** (Access key и Secret key) к этому ведру. Это
   «логин и пароль» для программы; в CRM и в чат их вставлять не нужно —
   только в файл `.env` на сервере.
3. Допишите в `.env` рядом с `docker-compose.yml`:

   ```bash
   S3_ENDPOINT=https://s3.regru.cloud
   S3_BUCKET=karkas-backups
   S3_REGION=us-east-1
   S3_ACCESS_KEY=ВАШ_КЛЮЧ
   S3_SECRET_KEY=ВАШ_СЕКРЕТ
   S3_PREFIX=karkascrm
   ```

4. Примените настройки и проверьте выгрузку вручную:

   ```bash
   docker compose up -d
   docker compose exec -T crm node scripts/upload-backup.mjs
   ```

   В ответе будет строка `✅ crm-…db (…) → karkas-backups/karkascrm/…`. Откройте
   ведро в панели — файл должен быть там. Если вместо этого `❌ … HTTP 403` —
   неверные ключи, `HTTP 404` — неверное имя ведра, «хранилище недоступно» —
   проверьте адрес `S3_ENDPOINT`.

5. Поставьте выгрузку в расписание (каждый день в 04:30, после ночной копии):

   ```bash
   # crontab -e
   30 4 * * * cd /opt/karkascrm && docker compose exec -T crm node scripts/upload-backup.mjs >> /var/log/karkas-s3.log 2>&1
   ```

   Повторно одни и те же файлы не отправляются (список отправленного хранится
   в `/data/.uploaded.json`), поэтому трафик и место не расходуются зря.

**Как вернуть данные из хранилища.** Скачайте нужный `.db` из панели хранилища,
затем **Настройки → Данные и компания → Резервные копии → Восстановить из файла**
(или положите файл в том `karkascrm_data` и перезапустите контейнер). Проверяйте
восстановление на копии раз в квартал — непроверенная копия не считается копией.

**Если S3 не хочется.** Второй недорогой сервер (или место у того же хостера)
работает почти так же:

```bash
# раз в сутки забираем копии на резервную машину
rsync -az --delete -e ssh /var/lib/docker/volumes/karkascrm_data/_data/backups/ \
  backup@10.0.0.2:/srv/karkas-backups/
```

`--delete` держите только если уверены: при ошибке в пути он удалит файлы на
приёмнике. Надёжнее — `rsync -az` без удаления и чистка срока хранения средствами CRM.

Есть и «человеческий» способ без cron: раз в неделю скачивать копию кнопкой в
интерфейсе и хранить на рабочем компьютере или в облачной папке. Это хуже
автоматики (легко забыть), но лучше, чем ничего.

### 7.2. База: SQLite или PostgreSQL — что выбрать

CRM хранит всё в одном файле базы (SQLite). Для 50 сотрудников и нескольких
десятков тысяч сделок этого хватает с большим запасом: при нагрузочной проверке
50 одновременных пользователей отвечали без ошибок, время ответа — миллисекунды.
SQLite не требует отдельного сервера: нет «ещё одного процесса, который может
упасть», нет пароля к базе, копия — это просто файл.

**Что такое «другая архитектура».** Обычно под этим понимают схему
«веб-сервер + отдельный сервер базы данных (PostgreSQL/MySQL) + кэш (Redis)».
Плюсы: несколько приложений пишут в одну базу одновременно, базу можно
масштабировать отдельно, есть привычные инструменты у администраторов. Минусы:
сервисов больше, каждый нужно обновлять, настраивать доступы и резервировать,
а сбоев становится больше (упал сервер базы — встала вся CRM).

**Насколько сложно переехать на PostgreSQL при Docker.** Честно: это не «поменять
настройку». Нужно:

1. переписать все запросы к базе (в коде их сотни) — у SQLite и PostgreSQL
   разный синтаксис, типы и работа с датами;
2. добавить в `docker-compose.yml` сервис `postgres` с томом, паролем и
   healthcheck, а CRM переключить на него;
3. перенести данные (обычно через миграционные скрипты) и проверить отчёты;
4. настроить резервное копирование уже для PostgreSQL (`pg_dump` вместо копии файла).

Это недели работы и постоянное усложнение эксплуатации. Оптимальный момент для
такого перехода — когда база реально упирается в пределы одного файла: это
сотни одновременных *записей* в секунду или десятки гигабайт данных. Для отдела
продаж каркасного дома такого не будет ещё очень долго.

Если когда-то понадобится, честный промежуточный шаг — вынести чтение отчётов
на копию базы (в SQLite это делается режимом WAL, который уже включён), а
запись оставить одну. Без переписывания кода.

### 7.3. ИБП: зачем он нужен

UPS (ИБП, «бесперебойник») — коробка между розеткой и сервером с аккумулятором.
Если свет мигнёт или пропадёт на несколько минут, сервер продолжает работать от
аккумулятора, а когда заряд кончается — ИБП сам аккуратно выключает сервер
командой завершения работы (по USB-кабелю). Для чего это в CRM:

- **не рвётся запись в базу.** SQLite надёжен при внезапном отключении (журнал
  WAL включён, запись подтверждается после фиксации транзакции), но лучше
  выключиться штатно;
- **нет «холодной» перезагрузки.** После пропажи питания обычный сервер
  включается не всегда сам и может испортить файловую систему;
- **звонки и чаты не прерываются** — менеджеры не теряют работу.

Что достаточно купить: ИБП на 650–1000 ВА (примерно 4–8 тысяч рублей) держит
небольшой сервер 10–20 минут — этого хватает, чтобы пережить мигание или
короткое отключение. Подключите его по USB и включите в системе автозавершение
(`apcupsd` для APC, `nut` для остальных). Проверка простая: выдерните ИБП из
розетки при выключенном доступе к CRM в нерабочее время и убедитесь, что сервер
выключился сам и база открылась после включения.

Если ИБП нет, минимальная страховка — включить в BIOS автоматическое включение
после подачи питания (`Restore on AC Power Loss → Power On`) и держать свежие
копии в S3 из раздела 7.1.

## 8. Обновление

```bash
./scripts/update.sh
```

Скрипт забирает изменения из репозитория, пересобирает контейнер и перезапускает сервис. Данные не затрагиваются, перед миграцией схемы автоматически создаётся страховочная копия.

## 9. Диагностика

```bash
docker compose ps                 # статус контейнеров
docker compose logs -f crm        # логи приложения
docker compose --profile tls logs -f caddy   # логи HTTPS-прокси
curl -s http://127.0.0.1:8080/api/health     # проверка приложения (без входа — только факт работы)
```

`/api/health` без авторизации отдаёт только `ok`, версию и время работы — этого достаточно
для healthcheck и мониторинга. Счётчики клиентов, размер базы и список резервных копий
видны только администратору: `curl -H "Authorization: Bearer <токен>" http://127.0.0.1:8080/api/health`.

Типовые причины недоступности:

- сертификат не выпускается — проверьте DNS домена и открытые порты 80/443;
- не приходят вебхуки — проверьте публичный адрес и секрет вебхука в настройках канала;
- не отправляется почта — нажмите «Отправить тестовое письмо» в настройках почты, ответ сервера покажет причину;
- вход не принимается — после серии неудачных попыток IP временно ограничивается, счётчик сбрасывается через 5 минут.

## 10. Контрольный список безопасности

- [ ] `JWT_SECRET` задан длинной случайной строкой, пароль администратора сменён.
- [ ] Боевой сервер работает только по HTTPS, `CRM_BIND=127.0.0.1`.
- [ ] Сотрудникам выданы роли по принципу минимальных прав, бывшие сотрудники деактивированы.
- [ ] Резервные копии настроены и проверено восстановление.
- [ ] Сервер получает обновления безопасности ОС и Docker.
- [ ] Ключи интеграций хранятся в `.env` с правами `600` либо введены через интерфейс.

## 11. Запуск без Docker

Для разработки или отладки достаточно Node.js:

```bash
./run-local.sh                      # http://localhost:8080, база в ./data
PORT=3000 ADMIN_PASSWORD=пароль ./run-local.sh
```

Пример unit-файла systemd для постоянного запуска без Docker:

```ini
[Unit]
Description=KarkasCRM
After=network.target

[Service]
WorkingDirectory=/opt/KarkasCRM
Environment=NODE_ENV=production
ExecStart=/usr/bin/node --experimental-sqlite backend/src/server.js
Restart=always
User=karkas

[Install]
WantedBy=multi-user.target
```

## Локальная проверка без настроек

`docker compose up --build` работает без `.env` и домена: http://localhost:8080.
Порт по умолчанию привязан к 127.0.0.1. Учётные данные первого входа:
`admin@example.com` / `admin12345` — только для локального теста.
Профиль `tls` проверяет наличие домена и нешаблонных секретов при запуске Caddy.
Эти проверки не заменяют настройку firewall, DNS и смену пароля в уже существующей базе.
Для тестовых данных и формата таблиц см. README; результаты аудита — AUDIT.md.

## Проверка после TLS-запуска

```bash
docker compose --profile tls ps
docker compose logs --tail=100 crm caddy
curl --fail https://crm.example.ru/.well-known/health
```

Замените домен в последней команде своим. Проверьте вход, создание сотрудника,
обязательную смену пароля, загрузку файла и резервную копию. Если сертификат не
выдан, проверьте A/AAAA, firewall и доступность 80/443 извне. `ACME_EMAIL` необязателен;
если заполнен, скрипт передаёт его Caddy. Домен указывайте без протокола, порта и пути,
кириллические домены — в punycode. Секреты с `$` в `.env` заключайте в одинарные кавычки,
чтобы Compose не интерполировал их; проще использовать сгенерированные hex-строки.
Не переносите локальную тестовую базу с известным паролем в production: изменение
`ADMIN_PASSWORD` в `.env` не меняет пароль уже существующего администратора.
